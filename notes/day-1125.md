## 三、产物决策：**走 B（逻辑过期）**，理由是"没时间回头补"

| 方案 | 内容 | 他的决定 |
|---|---|---|
| A | 只用互斥锁 | — |
| **B** | **加逻辑过期** | ✅ **选 B** |

他的原话：
> "**直接进 B 吧，补讲没关系**。用 A 之后回过头来补 B 我暂时认为没有这个时间，因为后面还有很多要学，**直接接近生产就好**，之后我自己复习即可。"

⭐ **我这边发现的重要事实（纠正我自己的判断）**：
> **逻辑过期的最小实现"懒重建"根本不需要 `setInterval`** —— 它是"读到 `expireAt` 已过 → 返回旧值 + 起一个异步重建"，只用 `Map`（去重）+ `Promise`，**都是①档已学**。
> 所以逻辑过期的核心 **不需要补讲**；补讲 `setInterval` 是为**"定时刷新"变体（冷数据用）**，属于额外收获。

**产物的实现选择**：**懒重建为主**（热点）＋ **`setTimeout` 递归作为可选定时刷新**（冷数据）。**不用 `setInterval`**（不等待上一次完成 → 会重入）。

### 块 B 两题

| # | 答案 | 判 |
|---|---|---|
| **1** | 选布隆过滤器（判断"不存在"100% 正确 + 挡在缓存前 + 缓存空对象也要进 DB 会很慢） | **✓ 结论对**，但**漏了决定性理由**：**随机 id 攻击下「缓存空对象」内存会被撑爆**（攻击者每换一个 id 就多缓存一条空）；也**没提布隆的代价**（要预热 / 1% 误判 / 不能删除） |
| **2** | 击穿 → 选互斥锁，理由"首页配置要求一致性，牺牲等待换一致性" | **◐ 方案可能对，理由错了**。首页配置恰恰是"旧一点没关系"的典型（配置晚 1 秒生效，用户感知≈0）；而 3000 QPS 卡在锁上 → 页面全白。**正确判据是「重建耗时」**：<100ms 用互斥锁；>1s 用逻辑过期。首页配置是单条 SQL（<100ms）→ 所以选互斥锁**结果对**，但理由必须换成"重建很快" |

### 块 C 三题（**全对**）

| # | 答案 | 判 |
|---|---|---|
| 1 | 击穿=单 key 过期+大量访问；雪崩=多 key 同时过期打垮系统；击穿用互斥锁、雪崩用 TTL 打散，因为"一个 vs 多个、宏观 vs 微观" | **✓✓**，只需收紧一处措辞：TTL 打散防的是"**同时过期**"，不是"同时击穿" |
| 2 | 一个响应一次往返，分到多节点后客户端要问每个节点，**一个往返变成好几个** | **✓✓** |
| 3 | 用 `now` 和 value 里的过期时间比较；定时扫描的问题是**"刚扫描完就过期 → 很长一段时间都是旧数据"**，热点 key 不允许 | **✓✓ 答出了深层原因** |

**Q3 我补的一句**：**定时扫描不是没用，它是给"冷数据"用的** —— 冷数据没人读，懒重建永远不触发，只有定时刷新能保鲜。**热点懒重建，冷数据定时刷新。**
