## ① 读的 5 行（**不抄文档**）

1. 测试金字塔：单元 / 集成 / E2E 各测什么、为什么"冰淇淋筒"是反模式 →
单元是对单个函数的测试 集成是的对多个模块的测试 E2E是测试整个系统的。
为什么反模式：数量上测试E2E比单元测试多，因为E2E测试时间长，寻找bug难，维护成本高，导致的结果是开发者不愿跑测试，修测试比写功能还累。
E2E多了反而
2. 单元 vs 集成的分界线（跨进程 / 真 IO / 用框架，有一个"是"就是集成）→
集成和单元的分界线看三个问题：
1. 是否依赖真实的外部资源？（真IO）
2. 是否跨越多个模块、层或组件？
3. 是否需要真实运行环境？

3. 怎么测 HTTP（为什么"起真服务 + fetch 打"比 mock 值；`buildServer()` 为什么不许自己 listen）→
测http的方式 mock模拟或者起真服务+fetch。为什么比mock值？因为mock测试有时候会骗过开发者，比如测不到路由是否真对，测不到序列化等等。；`buildServer()` 为什么不许自己 listen？因为构建和启动要分离，放在buildServer里将无法控制listen的开关，如果遇到多个文件还会出现抢3000的情况。在模拟请求用app.inject的时候不需要listen但仍然会执行
4. 测试数据库隔离（为什么 `mkdtempSync` + `DB_FILE`；为什么"换进程再看"才证明落库）→为什么 `mkdtempSync` + `DB_FILE`：测试需要一个干净可控可重复的数据库状态，直接用数据库，共享数据库 = 共享状态 = 测试之间产生隐式依赖。所以需要 `mkdtempSync` + `DB_FILE`造临时库
为什么"换进程再看"才证明落库：防止出现BEGIN事务在传没有结算这种情况，能发现并修改代码
5. 覆盖率的陷阱（行覆盖 ≠ 行为覆盖；分支覆盖更诚实；100% 也盖不住"漏掉的行为"）→行覆盖率只说明代码被执行，不说明行为被验证。每个 if/else、switch、三元表达式的每个分支，是否都被执行过。覆盖率高，不等于断言正确。
覆盖率只能衡量“已有代码被执行的程度”，不能衡量“需求被覆盖的程度”。

4. 三者对比


| 对比类别 | 单元测试 | 集成测试 | E2E 测试 |
|---|---|---|---|
|范围|一个函数/类|多个模块|整个系统|

5. mock 一般用在单元测试 
测试原则：能真则真，只有外部不可控依赖才 mock。

6. 行覆盖率只说明代码被执行，不说明行为被验证。
覆盖率高，不等于断言正确。

`if (age >= 18) {
  return '成年'
} else {
  return '成年'   // 写错了
}`
checkAge(20) 返回 '成年'；
checkAge(10) 也返回 '成年'，但测试没有断言，所以不报错。

覆盖率只能衡量“已有代码被执行的程度”，不能衡量“需求被覆盖的程度”。

好的测试策略是：

关注行为，不只关注行数；

分支覆盖率优先于行覆盖率；

边界和异常必须覆盖；

覆盖率作为参考和底线，不作为唯一目标。

## 补 10/5 未做

 把 COMMIT/ROLLBACK 都删掉那次：为什么同一个连接查是 4 条、换个新连接查是 0 条？
 因为连接还建立着，但实际上数据直接一直处于待传没有结算的状态，未提交的改动只有发起它的那条连接看得见，一旦切换新连接，因为别的连接只能看到已提交的，所以新连接查的是0条，如果待提交的连接关闭数据直接自动回滚，也查不到连接了
这条机制今天在哪儿会用到？（提示：三份老判据里有一条专门干这件事）
tasks-crud.test.js 的 06 跨进程持久化 就是专门干这件事的：它 spawn 一个全新的 node 进程、指向同一个 DB_FILE，重读 → 数据还在。换连接 / 换进程再看，才叫"真的落盘"（防的是"内存数组假数据库"）。
今天你亲手会碰到两处：契约第 10 条（PATCH done → 再 GET 确认）和第 12 条（DELETE → 再 GET 404）。注意它们证明的是"同一连接里改过了"这一档；最强的那档是 06 那种"换个进程再看"—— 所以你写测试时，06 可以当参照。
反过来还有个大用处（正好接你日志 §② 第三问）：这机制是"测试必须换临时库"的另一半原因 —— 打 data/tasks.db 的话，上一个测试已提交的脏数据，下一个测试看得见（提交了 → 别的连接就能看到）→ 测试之间开始互相依赖、顺序一换就红。
